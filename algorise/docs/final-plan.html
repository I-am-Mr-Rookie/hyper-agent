Founder-approved scope. Specified to be end-to-end executable by the Executor; items marked "Executor's choice" are the explicitly reserved degrees of freedom.

Consent-first user flow (frozen)

  1. Install and pair: user installs the extension, opens AlgoRise settings, and copies a one-time pairing code (or clicks a pairing deep link) into the extension. The extension exchanges it for a scoped upload token tied to the user's AlgoRise account. Tokens are rotatable and revocable server-side.
  2. Connect a platform: the popup shows the four platforms with Connect buttons. Clicking Connect only opens that site's own login page in a normal tab - the extension never sees, stores, autofills, or submits credentials, and never automates login. The user logs in manually or is already logged in.
  3. Handle confirmation: the extension detects the signed-in handle from the user's own session and asks "Detected handle X - is this you?" before anything is collected.
  4. Explicit per-platform consent: a consent screen states exactly what will be collected (the user's own submissions: metadata and source code), where it goes (their private AlgoRise account, used only for their skill/style analysis), and that they can pause, cancel, disconnect, or delete at any time. Sync starts only after the checkbox.
  5. Sync: background collector runs a single-concurrency, politely throttled queue (about one request per 2.5 seconds with jitter - Executor's choice to tune), with progress UI, pause/cancel, and a resumable cursor. First run is a bulk backfill; afterwards incremental (new submissions only). No collection ever runs without a user-initiated sync.
  6. Preview and upload: batches are shown (counts per platform, excludable) and uploaded to the platform API; the server deduplicates by platform + submission id.
  7. Revoke and delete: per-platform disconnect, plus a delete-imported-code action that calls the platform's deletion endpoint (ties into the privacy risk row and Section 12 checklist).

Invocation contract (binding on the Executor)

  • Client: one server-side gateway module wrapping the official OpenAI SDK with baseURL override per provider. No AI call anywhere else in the codebase; no key ever reaches the browser bundle.
  • Thinking-level mapping: send the slot's level as reasoning_effort (OpenAI-style); if the gateway uses the OpenRouter-style reasoning: effort object, the adapter translates. If the provider rejects the parameter (400/unknown-param), strip it and retry once.
  • Hard-coded fallback (pre-authorized by the user): when a provider cannot express thinking level at all, the Executor hard-codes high effort for every slot in high_stakes_slots - either by choosing an inherently high-effort model ID (the founders can encode effort in the ID itself, since IDs pass through verbatim) or by pinning the strongest available configuration. Never silently downgrade a high-stakes slot.
  • Reliability: timeouts (60s non-streaming), exponential backoff (max 3 tries), provider failover to secondary when configured, JSON-schema outputs where supported with local validation fallback.
  • Observability and cost: every call logs slot, model ID, tokens, latency, and estimated cost into llm_usage_log; daily budget envs enforce cutoffs; LLM_KILL_SWITCH=true disables all AI features gracefully (site keeps working without them).
  • Secrecy: .env gitignored; CI secret-scan on every push; keys server-side only; this plan contains placeholders only. Amendment A2: the executor chat receives live keys by founder decision - the executor writes them straight into untracked .env, never echoes, logs, or commits them, and the founder rotates every key after the run.
